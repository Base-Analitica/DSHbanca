# Viabilidade de UI acadêmica restrita ao preset `banca-auditor`

- **Issue:** [#70](https://github.com/Base-Analitica/DSHbanca/issues/70)
- **Investigação:** 2026-11-05 — somente leitura
- **Resultado geral:** **BLOCKED** para a exigência estrita de comprovar o preset efetivamente composto no Agent ativo; há superfícies de UI e leitura de arquivos compatíveis, mas elas não resolvem a prova de identidade nem a ocultação integral de metadados restaurados.
- **Base autorizada:** `origin/master` em `4698c36dfa941ff3d7922be1bc0030b4c5b94209` (merge da PR #72). A branch dedicada `docs/dshbanca-preset-ui-feasibility` parte diretamente desse SHA.

> O contrato de produto em [`docs/product/academic-workspace-design-contract.md`](../product/academic-workspace-design-contract.md#L34-L63) foi preservado. Este relatório é a única entrega autorizada. Não implementa UI nem altera ferramentas, perfil, rubrica, fluxo de decisão, permissões, issues ou dados de projeto.

## Resumo executivo

A projeção de Session é um candidato importante para a gate; não pode ser promovida a atestado do Agent vivo sem garantia adicional do DSH. Não se deve iniciar uma implementação parcial nem declarar clearance/release.

## Identidade: projeção de Session não comprova composição viva em todos os caminhos

A API Host `agentPresets.composedPreset(ctx): string | undefined` consulta a composição de um Agent ligado ao contexto; `inspectCompositions(ctx?)` também pertence ao Registry do Host. A Remote API disponível ao Client publica `agentPresets.list`, `read` e `select`, mas não `composedPreset` nem `inspectCompositions`. O Client recebe valores Host-computados via `useProjection`; não dobra os eventos do log por conta própria. As declarações instaladas e a implementação estão inventariadas acima.

`agentPresetProjectionDefinition` tem schema `string | null`, inicializa pelo `header.agentPreset ?? null` e só muda ao dobrar `agent-preset/selected`. A documentação do Registry identifica essa projeção como a identidade atual da Session, em vez do cabeçalho histórico isolado. No caminho comum de seleção, `select()` verifica que a Session ainda não começou seu primeiro turno, recompõe o Agent e appende o evento de seleção; depois do primeiro turno, a seleção é bloqueada. Isso torna a projeção um sinal Host-owned útil para a identidade de Session no fluxo normal.

O limite decisivo é que `AgentPresetRegistry.recompose(ctx, id)` também é público: a implementação monta a composição e emite `tools/change`, mas não appende `agent-preset/selected`. `select()` faz esse append somente depois de chamar `recompose()`. Portanto, o Client não pode deduzir, de forma geral, que a projeção corresponde ao mount vivo do Agent: uma recomposição direta deixa a projeção anterior intacta; durante uma seleção normal, a atualização projetada ocorre somente depois da recomposição. A Remote API também não devolve revisão, disponibilidade do Agent ou watermark de composição.

O Client ainda distingue abertura de histórico (`SessionSnapshot.openState: cold | loading | open | error`) de composição/availability do Agent. Resumos frios podem conter dicas `cached`; elas não são equivalentes a um baseline `sequenced` da conexão corrente. Deve-se rejeitar `undefined`, `null`, Session não aberta, erro, preset desconhecido ou dado apenas de cache como elegível. Mesmo aguardar `openState === "open"` não resolve a lacuna: esse campo é lifecycle do histórico, não atestado da composição ativa. Embora o DTO Host `SessionSummary` inclua `agentAvailable`, a interface `SessionSummary` usada pelo Client expõe `projectionValues` e omite esse campo; nenhuma dessas interfaces informa qual revisão de composição está montada.

A integração atual do DSHbanca tampouco transforma o guard do Host em API de autorização visual: [`src/dsh.ts`](../../src/dsh.ts#L100-L159) tenta consultar `composedPreset` no contexto de Agent durante dispatch e é uma política deny-only de tools; [`src/dsh.ts`](../../src/dsh.ts#L223-L229) registra esse guard no Host. Ela não controla navegação ou renderização do Client e não deve ser reutilizada como substituto de uma capability visual.

**Classificação:** a projeção `agentPreset` é **COMPATIBLE** como identidade Host-derived de Session no fluxo normal e após replay válido; a alegação mais estrita “o mount efetivo do Agent atualmente está composto como `banca-auditor`” é **BLOCKED**. Para desbloqueá-la, o DSH precisa oferecer um sinal Host-owned, session-bound e reativo, atualizado de maneira atômica em todos os rebinding (inclusive `recompose`) e que permita falhar fechado em reconnect/erro; ou documentar e garantir que toda troca viva use exclusivamente um caminho que mantenha essa projeção sincronizada. Não criar identidade paralela no Client nem inferir a partir do nome do preset instalado, do cabeçalho, do texto selecionado, da lista do Registry ou de prefixos.

## Superfícies Client e lifecycle de abas

| Superfície observada/instalada | Escopo/identidade disponível | Consequência para esta feature |
|---|---|---|
| `main` | Root/global; sem `sessionId` de uma Session selecionada no contrato do slot. | Não é a primeira escolha para uma UI que depende de preset da Session ativa. Uma contribuição ali é global até que o host prove outro contrato. |
| `conversation.view` | Session-scoped; hooks de Session e projeção, incluindo `sessionId`. | Melhor candidato nativo para um workspace central manuscript-first. A inscrição é, contudo, uma declaração de navegação global sem predicate de elegibilidade por Session; ocultar apenas o corpo ainda pode deixar item/label em outras Sessions. |
| `rightbar.session` e `sidebar.right.pane.tab` / `.title` | Session-scoped; título/corpo recebem contexto de tab e podem consultar hooks da Session. | Bom lugar para preview auxiliar de fonte/findings. Isso não torna a declaração do tipo, guia ou layout persistido automaticamente condicional ao preset. |
| `sidebar.right.tab.document` | Preview nativo em arquivo, no endereço completo da Resource/Session. | Pode abrir `.tex` como texto simples/código e localizar linha; pode renderizar PDF já existente. Não é, por si só, um changeset acadêmico nem prova que o PDF veio do fingerprint atual. |

O `main` ao vivo tem ocupantes nativos, mas não identificador de Session no standard props de root; `conversation.view` é a alternativa contextual. Ainda assim, seu item de navegação pertence a um slot/lista registrada globalmente, e a API examinada não oferece `visibleWhen(sessionId, predicate)` para ocultar o registro inteiro. Não foi comprovado se inscrição dinâmica num contexto de Session consegue remover sem corrida os itens de outras Sessions; não tratar isso como solução pronta.

No sidebar, a definição `SidebarRightTabDefinition` registra um tipo globalmente. `canOpen(address)` é um veto síncrono baseado no endereço, não um callback que recebe a identidade/estado atual da Session. `title(address)` é calculado no open e seu texto inicial é capturado no layout. O slot keyed de título pode fornecer um título dinâmico, mas é uma camada opcional sobre o registro/tab já persistido.

Os layouts do sidebar ficam em armazenamento por Session (`dsh.sidebar-right.v1.<sessionId>`) e são restaurados antes de montar os corpos; isso ajuda a separar estados entre Sessions. O registro persistido contém identidade/seleção/divisões/flutuantes, não o conteúdo do recurso, e o provider pode reconstruir o corpo pelo endereço. `keepMounted` é `false` por padrão; `true` retém corpos visitados através de ocultação, troca de Session e docking. O slot de tab também expõe `visible` como estado de apresentação, não como autorização. O `signal` da tab encerra com remoção do registro ou unload do plugin, não simplesmente por ocultar ou trocar Session. Callbacks e tarefas assíncronas precisam, portanto, revalidar a Session elegível antes de cada leitura/efeito e não depender de hide/switch para abortar.

Isso torna obrigatórios testes específicos de label estático, guia/menu/ações, floating e docked tabs restauradas, corpo montado, troca de preset enquanto a mesma Session permanece aberta, mudança de Session, reconnect e disposal. A persistência nativa protege a distinção entre layouts de Sessions; não protege contra revelar uma tab academicamente marcada/restaurada quando a Session já não satisfaz o predicado. **Não há clearance de isolamento sem E2E** para todos esses caminhos.

## Preview de fonte, navegação e diff nativo

O pacote instalado `@deepseek-ai/dsh-client-ui-sidebar-files` abre arquivos como `dsh-resource://file/session/<sessionId>/<path>` no pane da Session. O `@deepseek-ai/dsh-client-ui-sidebar-documentpreview` aceita código/texto simples, Markdown, PDF e outros formatos; texto desconhecido tem fallback simples. A API de tab pode abrir um endereço Resource e passar posição de linha. A identidade contém Session e caminho, o que permite uma navegação nativa e isolada por Session quando o próprio caller valida que o endereço pertence ao binding esperado.

Isso comprova uma opção nativa para abrir fonte `.tex`/`.bib` e um PDF que já existe. Não comprova um canvas central manuscript-first pronto: o preview descrito é do sidebar; um `conversation.view` central exigiria sua própria composição React no slot Session-scoped. Também não associa automaticamente o Resource lido ao fingerprint do finding; link de evidência stale/órfão tem de falhar fechado.

O `@deepseek-ai/dsh-client-ui-deliverables` oferece comparação nativa dos arquivos que o Host registrou como alterados ao término de um turno. Essa comparação é útil como inspeção **depois** da alteração do turno, não como o diff read-only de uma proposta concreta que precisa ser examinada antes da aprovação/aplicação. A síntese de `banca_contract`, o próximo passo textual `gerar_diff_proposto` e manifests de snapshot não preenchem essa lacuna. O contrato do produto exige preservar hashes do original, da proposta e do resultado aplicado e manter proposta/diff read-only em [`docs/product/academic-workspace-design-contract.md`](../product/academic-workspace-design-contract.md#L27-L32) e [`docs/product/academic-workspace-design-contract.md`](../product/academic-workspace-design-contract.md#L44-L50).
